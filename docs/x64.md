# x64

SOS2's x64 system runs in QEMU's microvm, on the virtio-mmio devices the
ARM machines use, and as a [PC](#pc), started by UEFI from a USB stick, so
far on QEMU's emulated one (q35 with OVMF); both under KVM on an x86 host or
emulated (TCG). Real PCs come next (see [Not yet](#not-yet)).

## Build and run

The x86_64-elf cross toolchain is built here, from pinned GNU sources: there
is no prebuilt one like the Arm GNU Toolchain.

```sh
make ARCH=x64 fetch      # the engine's sources and the toolchain's
make ARCH=x64 toolchain  # binutils 2.43.1 and GCC 14.2 into .tools/x86_64-elf
make ARCH=x64            # the kernel and the filesystem tools
make ARCH=x64 engine     # the runtime, WebKit, the updater, the apps and the bundle
make ARCH=x64 run        # the desktop in QEMU's microvm
make pc                     # a PC's USB stick (build/pc/sos2-pc.img)
make pc-run                 # that stick on QEMU's PC, under OVMF
```

It needs `qemu-system-x86_64`, NASM (FFmpeg's assembly) and, for KVM, access
to `/dev/kvm`; without it QEMU emulates the CPU (`RUN_ARGS='--accel tcg'`
forces that). The display is virtio-gpu, since microvm has no ramfb. virgl
(`RUN_ARGS='--graphics virgl'`) is built as for the ARM machines but not yet
tried on x64. microvm has no power key, so standby is not reached there;
on the PC, QEMU's Machine > Power Down presses ACPI's power button. `make pc`
needs OVMF (the `ovmf` or `edk2-ovmf` package; `OVMF_CODE` and `OVMF_VARS`
name others), and `STORAGE=persistent` makes the stick keep its data, as an
installed system does; `RUN_ARGS='--pointer mouse'` gives `make pc-run` a
relative USB mouse in place of the tablet, which follows the window's
pointer.

## Boot

The kernel is linked at 64 MiB, clear of what UEFI firmware keeps low down
while it runs (OVMF's decompressed firmware volumes reach about 29 MiB). On
microvm, QEMU loads its ELF itself, through its PVH note
(`arch/x64/boot.S`): the kernel starts in 32-bit protected mode with paging
off, identity-maps the low 4 GiB with 2 MiB pages (uncached from 3 GiB, where
the devices' MMIO lies; on a PC all write-back, its RAM reaching past 3 GiB
and its MTRRs keeping the MMIO uncached), enters long mode and calls `x86_boot`
(`arch/x64/cpu.c`), which sets up the boot CPU and measures the TSC before
`kernel_main`. QEMU's PVH start info stands in for a device tree
(`arch/x64/machine.c`): the memory map, the initrd (the resource bundle, as
on arm64) and the command line with the `sos2.*` arguments; ACPI gives the
CPUs (MADT), the IOAPICs and the reset register (FADT). QEMU lists microvm's
virtio-mmio devices on the command line only for Linux, so on QEMU, whose
ACPI tables are BOCHS's, the kernel looks for its transports at their fixed
addresses from 0xfeb00000. QEMU puts the initrd against the top of RAM below
4 GiB, where microvm's firmware (qboot) reserves pages for itself, with a disk
attached some the initrd is then loaded over: the module list wins, and its
range is taken out of the firmware's reservations. The CMOS clock gives the
time until SNTP. A PC starts differently: see [Its loader](#its-loader).

## CPUs, interrupts and time

Up to eight CPUs run, as on arm64. The others start through INIT and two
STARTUP IPIs at a real-mode trampoline copied below 1 MiB, which enters long
mode on the kernel's own tables; each finds its record by APIC ID
(`arch/x64/smp.c`). The mailboxes and the epoch rule are arch/arm's. An
idle CPU polls its mailbox for about 50 us, then halts with interrupts on,
and CPU 0 sends a wake IPI only to a halted one: under KVM an idle CPU leaves
its host core to others.

The kernel takes three interrupts: each CPU's scheduler timer (the local
APIC's TSC-deadline mode, or a one-shot count calibrated against the TSC under
TCG), the wake IPI and the APIC's spurious one. The 8259 and every IOAPIC
input stay masked: the drivers poll, as on ARM (`arch/x64/apic.c`). The
kernel's counter is the TSC shifted right by 4, so that the shared 32-bit
frequency holds any TSC's; its frequency comes from QEMU's timing leaf (CPUID
0x40000010, with `invtsc`), CPUID 0x15, or the PIT's channel 0 (microvm has no
port 0x61 for channel 2). User code reads the TSC itself; a process gets the
frequency in r10 at entry.

## Traps and system calls

A user slice ends in IRETQ (`arch/x64/entry.S`). Every trap from user mode,
SYSCALL, the timer or a fault, saves the user's registers straight into the
CPU's `struct cpu_trap` through GS and returns from `cpu_user_run`, as arm64's
`arm_user_run` returns. Exceptions run on each CPU's exception stack (IST1),
NMI, double fault and machine check on a stack of their own (IST2); a kernel
exception is fatal. System calls are SOS2's own ABI, used only by the SDK: the
number in rax, arguments in rdi, rsi, rdx and r10, and the result in rdi, so
that the shared dispatcher reads and writes the same slots as on ARM
(`arch/x64/include/arch/context.h`). User state is FXSAVE's: the system
targets x86-64-v2 and leaves AVX off (no OSXSAVE), so every library takes its
SSE paths. SMEP and SMAP are on where the CPU has them.

## Memory

Each address space's PML4 points, from its entry 0, to a PDPT laid out like
arm64's level 1 root: the kernel's global identity map of RAM below 4 GiB, and
from 0x10_0000_0000 the process's own tables (`arch/x64/mmu.c`). Devices
may lie anywhere: those past the first 512 GiB (OVMF puts 64-bit PCI windows
high) are mapped through PML4 entries of their own, which every space shares,
and a window needed before the kernel's tables (a PC's xHCI, whose stick is
read early) goes into boot.S's map too. Every page is write-back, devices'
MMIO uncached and a framebuffer write-combining (PAT): x86's DMA is
cache-coherent, so the kernel keeps no uncached data and maintains no
caches. Writable memory is
never executable outside the engine's JIT window (64 MiB, as on arm64). The
shared engine block is mapped with 2 MiB pages; QEMU places the initrd on a
4 KiB boundary, so the kernel copies the engine into an aligned block at its
first page rather than using it in place. Entering a space writes CR3, which
drops its translations; the kernel's own are global.

## SDK

x64's TLS is variant 2: the TLS block ends at the thread pointer, FS's
base, whose first word points to itself (`sdk/runtime/threads.c`). User code
cannot change FS (no FSGSBASE); `SYS_THREAD_TLS` sets it, first to a bootstrap
TCB before anything reads it. Programs are RIP-relative (`-fpie`) and linked
without PIE at 0x1010000000, beyond the small code model's absolute addresses;
`--no-relax` keeps ld from turning GOT loads into 32-bit absolute immediates
there. The toolchain's GCC puts static constructors in `.init_array`, as
the Arm toolchains do: configured for a cross target it would guess `.ctors`,
which nothing runs, and the linker script refuses them. x64's Newlib
leaves the POSIX calls to the system, so libsos2 defines `read` and the
others itself. Native apps are built for the x64 ABI (`USER_ABI_VERSION`
carries EM_X86_64, 62).

## Engine

JavaScriptCore runs its interpreter and its baseline and DFG JIT tiers, as on
AArch64 (the FTL tier needs WebAssembly). x64 takes the arm64 patch's
64-bit fixes and one patch of its own (`wpe-2.52.6-native-x64.patch`):
2.52.6 turns AVX on from CPUID's AVX bit alone, and its VEX instructions would
fault here, where the kernel saves no AVX state, so it also asks for OSXSAVE
and XCR0's AVX state; it also reads BMI1 and AVX2 from the right register.
FFmpeg (NASM's assembly, `--enable-pic`) and Skia check for AVX the same way
at run time and take their SSE paths. Under KVM on an i9-12900KF, a scratch
benchmark of twelve script kernels took 1.6 s on the interpreter, 0.50 s on
the baseline JIT and 0.21 s with the DFG (1.9 s emulated, under TCG), every
result matching Node's.

## PC

A PC (`boards/pc`, `SOS2_BOARD_PC`) is the x64 kernel with its own
drivers in place of microvm's virtio ones, all polled as everywhere else.
So far only QEMU's emulated PC runs it: q35 with OVMF, std VGA, xHCI with the
stick, a USB keyboard and a USB tablet or mouse, an Intel 82574L (e1000e)
and Intel HD Audio.

### The stick

`make pc` writes a GPT stick image (`tools/package_pc.py`, which writes the
FAT32 and the GPT itself):

| Partition | Size | Contents |
| --- | --- | --- |
| EFI system partition | 64 MiB | SOS2's loader, `EFI/BOOT/BOOTX64.EFI` |
| `sos2-system` | 64 MiB | the system image: the kernel's ELF and the resources as a SORZ ramdisk (`include/boot/pc_image.h`) |
| `sos2-data` | 192 MiB | the app store, then the data volume (`include/system_store.h`), formatted at the first start |

An installed stick keeps its data in `sos2-data`, as a phone keeps it in its
cache partition, and its updater rewrites `sos2-system` as a phone's rewrites
its boot partition (`kernel/protection/system_update.c` checks the image as
the loader will start it); `STORAGE=ram` makes a stick that keeps nothing.
`tools/web_content.py --stick` installs the local website in a stick's data
volume once SOS2 has formatted it. For `make publish`, `build/pc-install`
holds the installed stick xz-compressed (`sos2-pc.img.xz`, about 30 MB), the
updater's file and `install.json`; `make publish PUBLISH=x64` publishes
the PC alone.

A stick updates itself as the phones do: **UPDATES → CHECK FOR UPDATES**
reads `https://freshpsam.github.io/sos2/x64/sos2-x64.update` and the
x64 apps' `apps-x64/index.txt`; **INSTALL SYSTEM** downloads the
system image, about 31 MB, which the kernel checks and writes to
`sos2-system`, and **RESTART** starts it. Tried in QEMU: a stick of an older
build updated to the published release, the Calculator installed from Pages,
and web storage and cookies kept through a system write and a restart.

### Its loader

`boot/uefi/loader.c` is a UEFI application, linked as a position-independent
ELF and turned into a PE32+ by `tools/elf2efi.py`, with our own small
`efi.h`. It finds the GPT disk it was started from, reads `sos2-system`,
checks its CRC-32s, loads the kernel's segments where they are linked and
the resources below 4 GiB, keeps the firmware's GOP mode unless it has fewer
than 800 lines, and hands the kernel its boot information
(`include/boot/sos2_boot_info.h`): the memory map, the resources, the
command line, ACPI's root pointer, the framebuffer and the stick's GPT disk
GUID. It then leaves boot services and jumps to `uefi_start`, which builds
pvh_start's tables in long mode. A system partition it cannot start, such
as the cleared one an interrupted update leaves, it names on the screen.

### Its devices

- **Screen:** the GOP framebuffer, with the 480x800 desktop at the monitor's
  full height in its middle (648x1080 on a 1080p monitor), black bars
  beside it; panics take the whole monitor.
- **PCI** (`pci.c`): ECAM from ACPI's MCFG, the buses found mapped as one
  window, the memory BARs as the firmware assigned them, each driver's mapped
  with the kernel's devices.
- **USB** (`xhci.c`): every xHCI controller, taken from the firmware (Intel's
  7 and 8 series' shared USB 2 ports switched over from EHCI), its root ports
  enumerated at start and as devices connect and go; an endpoint that halts
  or times out is reset or stopped and started again. Keyboards in the boot
  protocol (`usb_hid.c`) type as `kernel/input.c`'s do, with its repeat;
  mice and tablets, read through their report descriptors, act as a finger,
  with a cursor drawn over the desktop (`kernel_board.c`).
- **The stick** (`usb_storage.c`): USB mass storage, bulk only, SCSI's block
  commands; of the sticks present, the one whose GPT disk GUID the loader
  passed. Copies of one image share their GUIDs, so with two plugged in the
  loader refuses to start and the kernel uses neither.
- **Network** (`e1000e.c`): the 82574L, legacy descriptor rings.
- **Randomness** (`entropy.c`): an HMAC_DRBG, as the phones', seeded from
  RDSEED or RDRAND.
- **Sound** (`hda.c`): HD Audio, the first controller whose first codec has
  an output pin with a path back to a DAC (a graphics card's HDMI-only one is
  passed over), one 48 kHz stereo stream over a 256 ms ring, as the Redmi 2
  plays.
- **Power button** (`acpi_power.c`): ACPI's fixed one, polled, after ACPI
  mode is turned on.

## Not yet

- **Real PCs:** Secure Boot (off, or a signed loader); Intel's I225 and other
  network cards; NVMe and AHCI, and installing onto an internal disk; real
  HD Audio codecs and HDMI's; USB hubs, which most PCs put their ports
  behind; PS/2; a GOP framebuffer above 4 GiB, and BARs inside the user
  window's physical range (64 to 68 GiB); a power button only AML reports;
  a stick larger than its image, whose backup GPT is not at its end; a boot
  stick that attaches late or is slow to become ready; firmware that hands
  over in unusual states (CR4 bits such as OSXSAVE left set, 5-level paging,
  an MCFG range starting past bus 0, more than 16 RAM ranges, duplicate APIC
  IDs).
- **Meltdown:** the kernel is mapped in every address space, so on CPUs
  affected by Meltdown (Intel's before about 2019) page scripts could read it;
  such PCs need KPTI-style split tables.
- **A desktop for monitors:** landscape, with desktop sites and the mouse's
  own buttons; the on-screen keyboard also opens beside a physical one.
- **Speed:** PCID (re-entering a space without flushing it), SYSRET, AVX state
  (XSAVE), and an SSE2 path for the media player's YUV scaler; a system
  update writes the stick a sector at a time.
